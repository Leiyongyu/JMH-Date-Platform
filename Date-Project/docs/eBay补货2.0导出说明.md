# eBay补货2.0全量Excel导出

更新日期：2026-10-16。

## 等级汇总、排序与负责人（2026-10-16）

- 安全库存、建议补货量、安全库存2、建议补货量2支持升降序；刷新时统一计算并保存结果，列表在结果表中执行SQL排序、筛选和分页，不再每翻一页都全量计算。四列空值始终排最后；导出沿用同一排序。金额与比率使用未格式化的数值排序，不以显示文本排序。
- 产品等级保留原下拉样式，选项展示 `等级（建议补货量合计 / 建议补货量2合计）`，选中后立即筛选。单位为件，不是SKU记录数。合计按当前站点、SKU、产品性质、销售类型、运营确认等其他筛选条件统计全部记录，不受分页或当前选中等级影响。
- `--` 表示无法计算等级，支持独立筛选。无法计算的建议量不计入合计，真实0保留；无记录的等级合计为0。编辑时效成功后的单行重新计算会同步调整所属等级及全部等级的合计。
- 最后新增负责人列，使用北京时间当天所属月份的 `dwd_performance_owner_rule`，限定 `platform=ebay`、`rule_type=EBAY_BRAND`，按SKU首段品牌匹配；跨站点同品牌同负责人。FLL/LEJ归方黎力、CL归陈丽，沿用绩效排名固定归属。当月缺规则或负责人为空时显示“未分配”，不回退其他月份。
- 列表返回 `level_summary`、`owner_rule_month`；负责人导出使用独立字段权限 `operations:ebayReplenishmentV2:exportColumn:principal_name`，不影响页面可见性。

## 读取与计算优化（2026-10-16）

- 数据链路：原订单及售后分类 → 按日/站点/产品SKU汇总 → 三个30天区间及7/15/30天条件聚合 → 复用现有等级、预测和补货公式 → 保存计算版本 → SQL筛选、等级合计、排序、分页。业务公式和SKU归并口径保持不变。
- 点击刷新强制检查源输入并重新计算；未变的数据也会生成新的计算时间。普通列表请求最多每5秒检查一次源内容，有变化时重算；跨北京时间日期或算法版本变化立即失效。这不是后台每5秒运行的定时任务，没有请求时不会自动运行。
- 源校验覆盖订单原地改写、删除和覆盖、售后分类、库存、刊登时间、库龄、规则、人工时效、负责人、仓租和汇率。订单/分类签名变化时，在事务内整表重建新日汇总表；当前不是逐日增量ETL。源签名检查仍需扫描/聚合源数据，不能把缓存命中耗时当成所有请求耗时。
- 同一MySQL实例上的命名锁合并并发构建；一致性读、日汇总更新、结果发布在事务内完成。构建失败回滚，旧版本保持可读。等待其他构建完成的刷新请求也重新校验输入，避免遗漏期间刚保存的人工时效。
- 计算结果保留最近20个版本；相同内容共享结果行，避免每次无变化刷新重复保存整表。版本保留仅用于页面和导出一致性，不是业务历史归档。仅清理这些新派生表中的过期版本，不删除原始订单或历史报表。
- 运营/开发备注、运营确认和销售类型仍保存在原人工表，查询时实时关联；计算不会覆盖它们。人工时效属于计算输入，与计算值一起保存在版本中，不再由Java用较新值覆盖。
- 等级下拉、列配置和权限保留；等级合计先应用其他筛选条件，再按等级汇总，不受页码影响。修改时效后单行回填，下一次导出前重新读取完整页面计算版本，避免混用不同版本的指标。

## 订单SKU与站点口径（2026-09-28）

- 过滤 `AMZ` 开头和“数字+PC”开头的SKU（正则 `^(AMZ|[0-9]+PC)`）。仅 `PC` 开头不会因此排除。
- 末尾 `-YXR`、`-RXY` 为二手标记，去掉标记后与原SKU按同一站点汇总。其他后缀不截断，不跨站点合并。
- 列表、近7/15/30天订单量、月度订单指标、分页计数、导出及预估销量试算共用 `backend/services/ebay_order_product_key.py` 的产品键CTE。比率仍由归并后的分子与分母计算，不直接相加各SKU的比率。
- 搜索二手SKU会先转换为产品SKU，返回同一产品族。销售类型保存也使用站点和产品SKU，只有二手订单的产品仍可维护。
- 原始订单SKU不改写、不删订单，不需要重新导入订单。SKU归并规则本身无需改源表；本次读取优化需要新增下文的4张派生表。库存、刊登、仓租、人工时效等数据源的归并规则不因此改变。
- 本地2026年6～8月核对：原1699个站点/SKU，过滤1个，223个产品族发生合并，最终1465行（德国619、美国433、英国413）。逐行与原始订单独立汇总核对，搜索、试算、越界分页均通过；本地全量查询约1.39秒。该数量和耗时是本次本地快照，不代表部署环境。

## 使用方式

按北京时间当天为基准，不含今天：近7/15/30天截至昨天，原自然月改为连续三个30天区间；利润率、退货率按近90天汇总。已移除有单天数、ADI和顶部参数入口；运营/开发备注保存全文，运营确认可筛选。

页面工具栏保留“导出全部数据”，仓租上传入口已移除。仓租列与库存明细共用谷仓近30天明细快照 `date-project.ods_goodcang_wh_inventory_storage_detail`，按拉取月份 `dim_lingxing_currency_month.my_rate` 换算人民币；没有源快照或汇率缺失时显示 `--`，有快照但本站点SKU无收费记录时显示0。列表和导出使用同一取值。

- 没有筛选：导出当前补货2.0列表范围内的全部站点/SKU。
- 有筛选：导出当前站点、SKU包含搜索、产品等级、产品性质、销售类型、运营确认条件的全部匹配记录，顺序跟随当前排序。
- 不受当前页码、每页50/200条或隐藏列影响；不是导出所有历史订单。
- 要无条件导出，先点击“重置”，再点击“导出全部数据”。
- 时效或销售类型正在保存时应等待保存完成；按钮防重复点击，下载使用项目通用下载方法。

## 工作簿

1. **补货2.0**：最多38个数据列，包括仓租、三段人工时效、两组安全库存和建议补货量、运营/开发备注、运营确认和负责人。不导出“采购”等操作按钮。
2. **90天分段明细**：同一批SKU的三个连续30天区间，包含销量、毛利、退货量、产品质量问题退货量/率、退货金额及未分类退货量。
3. **导出说明**：生成时间、主表行数、统计月份、筛选条件、排序和空值说明。

数值以Excel数值单元格保存；金额2位，比例百分数2位，整数/天数不显示多余小数点。SKU和商品名称显式保存为文本，不丢前导零，也不把以等号开头的名称当作公式执行。缺失值为`--`，真实0保留；质量问题退货量/率为0时依页面口径显示`--`。表头冻结并可筛选。

主表和分段明细只保留角色有导出字段权限的列；某个Sheet没有可导出的业务列时不生成该Sheet。页面列显隐不决定导出权限。

## 接口与复用链路

- 前端/Java：`POST /operations/ebay/replenishment-v2/export`，表单参数为`site/sku/productLevel/productNature/salesType/operationsConfirmed/sortField/sortOrder/calculationVersion`，不接受分页参数。
- Python内部：`GET /api/v1/finance/ebay-replenishment-v2/export-data`，使用内部Token校验。
- 列表和导出均调用 `list_replenishment(..., use_read_model=True)`，再转 `ebay_replenishment_read_model.query`。导出设置 `paginate=False`，对同一结果版本执行相同SQL筛选和排序，不做分页。
- 列表新增 `refresh`、`exactSku`，Java转发为Python的 `refresh`、`exact_sku`；普通翻页/筛选不强制重算。内部旧路径保留作回归对照，页面不走旧全量内存排序链路。
- 版本结果已包含计算时的人工时效及仓租，Java不再二次补齐；无版本的旧接口结果仍保留兼容关联逻辑。
- Excel序列化只取已有计算结果，不复制计算公式；核对`items`数量与`pagination.total`，不一致则拒绝生成，避免把分页误当全量。
- 工作簿使用SXSSF，临时文件在完成/失败时清理；生成完整文件后才写下载响应。若超过Excel单表行数限制，明确报错，不截断。

新页面传入 `calculationVersion`，导出固定该版本的计算指标；人工备注、确认状态、销售类型取查询时最新值。超过20版本保留期时明确报“计算版本已过期，请刷新页面后重试导出”，不静默换版本。旧客户端未传版本时读取/构建当前版本。导出不调用领星、谷仓、eBay拉取任务，不修改业务源记录。数量的底层数值保留，显示精度按页面设置。

## 权限与部署

导出按钮和接口校验 `operations:ebayReplenishmentV2:export`，并由Java按 `operations:ebayReplenishmentV2:exportColumn:<字段>` 再次限制实际写入Excel的列。页面查看权限不等于导出权限，导出记录业务操作日志。

**新增4张派生表，不修改原业务源表结构。** 在Python应用库执行 `Date-Project/migrations/20261016_ebay_replenishment_read_model.sql`：

- `dws_ebay_replenishment_daily`：日/站点/产品SKU指标。
- `dws_ebay_replenishment_generation`：计算日期、输入签名、算法版本及元数据。
- `dws_ebay_replenishment_result`：用于排序筛选的标量列、索引和展示JSON；generation列保存内容版本键。
- `dws_ebay_replenishment_state`：当前计算版本和源检查时间。

脚本已在本地应用库执行并加入Python初始化迁移列表；部署机未执行、未操作。首次访问或刷新从已有源数据生成派生结果，不需要重新拉取数据。

另有负责人导出权限脚本 `RuoYi-Vue-springboot3/sql/20261016_ebay_replenishment_v2_owner_export.sql`，依赖已有 `20261016_ebay_replenishment_v2_export_columns.sql` 和 `20261016_ebay_replenishment_v2_export_menu.sql`。可重复执行，仅首次新增时给已拥有导出权限的有效 `admin` 角色默认启用负责人导出；其他角色由管理员勾选。不会重置既有字段授权。**本轮未执行负责人导出权限SQL**，不要与已执行的4张派生表迁移混淆。

部署需要先准备派生表，同步更新Python并重启、重新构建并重启Java、构建部署Vue前端。本轮没有自动重启当前服务、没有提交或推送；销售看板原有未提交改动保持不动。无需补跑上游数据任务或重新导入数据。
