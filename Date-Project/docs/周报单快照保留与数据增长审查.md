# 周报单快照保留与数据增长审查（2026-09-15）

## 本轮决定与改动范围

按用户要求，周报源数据最多保留一个完整成功批次。仅修改周报链路，不把一份策略套到月度业务历史或运行日志。本轮未调用领星、未执行业务数据库清理、未删除实际 Excel，未改变其他模块保留策略。

四张表必须按同一个 sync_batch_id 一起替换：

- ods_lingxing_inventory_detail_weekly
- ods_lingxing_inventory_age_bucket_weekly
- ods_lingxing_inventory_bin_detail_weekly
- ods_lingxing_product_info_weekly

空库龄/空仓位数据可能是合法结果，此时相应表为零行，不代表缺失批次。库存和产品数据必须完整。抽取仍保留全仓；只有 Excel 导出限定 18677（EU）和 19561（UK）。

## 提交与失败保护

1. 全链路沿用 inventory:weekly-export 互斥锁，与手动生成、删除文件互斥。
2. 完整拉取、分页与产品覆盖校验后，先生成新的独立 Excel 文件；此时不触碰旧快照。
3. 校验新批次、日期、产品覆盖与文件指标；锁定其 RUNNING 文件登记。
4. 显式 connection.begin() 后，同一数据库事务：四表 INSERT 新批次 → 四表 DELETE 其他批次 → 更新文件登记 SUCCESS → 一次 COMMIT。不能仅依赖 autocommit=False；显式事务也会阻止 DBUtils 对断线后的单条语句自动重连重放。
5. 插入、删除或登记失败时整体 ROLLBACK，上一份成功快照不变；不能用 TRUNCATE，也不能先提交删除。
6. 提交响应不确定时，错误登记只更新 RUNNING，不把已成功提交的 SUCCESS 降级。

稳定提交状态只保留一个批次；切换事务内部会短暂同时存在新旧数据，并需要相应事务日志空间。页面生成使用最新保留快照，不触发替换/清理，不写 ODS。文件登记、历史 Excel 不自动清理，删除按钮仍只删除用户选择的 Excel。

新 Excel 已生成但数据库事务失败时，该文件保留为失败证据，列表不将其标为成功；不冒险自动删除磁盘文件。源快照始终保留上一份。旧快照被新批次替换后，历史 Excel 仍可下载，但无法再从数据库重建旧时点的数据；删除旧 Excel 前需要注意这个限制。

## 部署与验证

- 部署周报 repository、sync service、页面与文案变更并重启 Python。本次保留策略不需要 Java 或数据库结构迁移。
- 无需手工清空表。下一次完整拉取且 Excel 生成、数据库事务都成功时，会在同一事务中清理旧版本已累积的所有其他批次。
- 仅点击“使用现有数据生成 Excel”不会清理当前已有历史批次，这是有意保持纯生成操作的边界。
- 旧数据清理后无法从数据库直接恢复，如还需保留历史，应在部署/下次成功拉取前完成独立备份。
- DELETE 释放的是 InnoDB 内可复用页；数据库物理文件不一定立即缩小。本轮不执行 OPTIMIZE TABLE 或表重建。
- `deleted_rows` 返回本次实际删除的四表总行数，进入现有任务指标/日志。`row_count` 仍为仓位展开后的 Excel 行数，两者含义不同。
- 极端情况下 COMMIT 已成功但响应丢失，任务可能记录失败；成功快照及文件登记仍保留，不会被错误登记降级。此时需核对任务日志与文件列表，不应直接清空重跑。
- 新增迁移不需要执行；原菜单 SQL 仅更新新建任务时的说明，既有调度与权限不覆盖。

以下是只读检查，不做删除（在 date-project 库运行）：

```sql
SELECT 'inventory' AS source_table, sync_batch_id, snapshot_date, COUNT(*) AS row_count
FROM ods_lingxing_inventory_detail_weekly GROUP BY sync_batch_id, snapshot_date
UNION ALL
SELECT 'age', sync_batch_id, snapshot_date, COUNT(*)
FROM ods_lingxing_inventory_age_bucket_weekly GROUP BY sync_batch_id, snapshot_date
UNION ALL
SELECT 'bins', sync_batch_id, snapshot_date, COUNT(*)
FROM ods_lingxing_inventory_bin_detail_weekly GROUP BY sync_batch_id, snapshot_date
UNION ALL
SELECT 'products', sync_batch_id, snapshot_date, COUNT(*)
FROM ods_lingxing_product_info_weekly GROUP BY sync_batch_id, snapshot_date;
```

新逻辑首次成功后，上述结果只应有同一个 sync_batch_id（合法空表没有行）。本轮验证使用离线模拟事务与临时 Excel，不替代部署机验收。

本地离线验证：`python -m pytest tests -q -k weekly` 为 225 passed、1 skipped；页面 Node 测试 5 passed；Python 编译检查通过。覆盖空批次/混批/日期不一致/产品缺失/文件指标异常拦截、四表替换顺序、插入与删除与登记失败回滚、提交响应不确定、只读重新生成、旧 Excel 保留。未连接真实数据库执行这些操作。

## 其他模块是否也在不断追加全量副本

以下限于仓库代码检查，未查询实际表大小、数据库事件或外部运维计划。行数/磁盘容量不能只从代码推断。

| 类别 | 代表表/模块 | 查到的实际行为 | 本轮处理 |
| --- | --- | --- | --- |
| AMZ 补货当前快照 | amz_replenishment_us_snapshot、amz_replenishment_eu_snapshot | 激活新批次后删除非当前批次，已保留当前一份 | 不改 |
| AMZ 当前库存 | amz_warehouse_inventory_detail、amz_product_performance_inventory | 事务内全量替换，不保留重复版本 | 不改 |
| 月度库存、绩效、滞销库龄 | AMZ/eBay 月度利润，月度库存三仓源表，FBA/eBay/CTU 库龄表 | 同 stat_month/pull_month 删除后重写；跨月保留业务历史，同月重跑不会多一份完整快照 | 不改，不应清为只剩当月 |
| Java 月度接口快照 | ods_goodcang_inventory_age_monthly；领星采购、供应商阶梯价、运输成本三张 monthly ODS | 同 snapshot_month 覆盖；跨月历史未见自动保留上限 | 不改，先保留历史报表所需数据 |
| eBay SKU/SOP 明细 | 订单原始与明细表 | 按订单/付款日替换、订单去重，部分来源按涉及月份替换 | 不改，新订单增长不是重复全量副本 |
| 运行日志 | scheduler_task_run、performance_refresh_run、data_sync_log、sys_job_log | 每次运行新增一条或少量记录；未发现已接入的自动保留期限 | 记录后续治理项，不清理 |
| 导入/文件登记 | ebay_sku_analysis_import_batch、etl_ebay_sop_import_batch、ops_weekly_export_file | 按导入或文件增加登记记录，不是复制所有源明细 | 保留追溯；文件由用户手动管理 |

`data_sync_log` 已有 cleanOldLogs/deleteOlderThan 方法，但本次未找到定时调用；`sys_job_log` 有手动清空入口。不能把“存在清理方法”当作“已经定期清理”。`performance_import_batch` 按类型/平台/月/文件哈希唯一，同一文件内容会更新原登记，不宜归为每次无条件新增。

### 主要源码依据

- Python：repositories/performance_repository.py 的各月度 replace/append（写入前按月删除）、clearance_repository.py、inventory_report_source_repository.py、inventory_report_etl_repository.py；ebay_sku_analysis_service.py 的订单键替换。
- Python 日志：scheduler_service.py 的 run_id、performance_service.py 的 refresh_id，以及 repository 的 INSERT/UPSERT。未找到对应历史清理路径。
- Java：AmzUsReplenishmentRefreshService / AmzEuReplenishmentRefreshService 与 AmzReplenishmentSnapshotMapper 的当前批次激活/删除；GoodcangInventoryAgeSyncService / LingxingProductProcurementSyncService 的同月删除。
- Java 日志：OperationSyncLogServiceImpl 与 DataSyncLogMapper；AbstractQuartzJob 与 SysJobLogMapper / SysJobLogController。

结论：除已处理的周报外，本次检查未发现其他明确的“每次重跑就追加整份全量快照”路径；另有需要业务历史的月度表与尚无自动期限的审计日志。两类不应直接复用周报的单快照删除规则。
