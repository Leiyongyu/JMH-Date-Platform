两表均有 `period_kind`，但两平台保存策略不同：

- **AMZ=MONTHLY**：同月汇总、明细在一个事务内替换，只有一份当前结果；月份变化不删除旧月。日期、源批次、负责人规则或店铺映射变化时，下次当月查询重算；未变化复用同月结果。当月历史趋势标记 `provisional=true`，表示尚未结束。
- **eBay=LIVE/FROZEN**：LIVE是当月物化缓存，FROZEN是月末首次成功冻结。历史只读FROZEN，旧LIVE跨月清理不影响FROZEN。
- 兼容已保存的旧版AMZ FROZEN历史，但绝不拿今天的源数据重算过去月份。新版本与旧版本不同，环比返回VERSION_MISMATCH。没有保存的月份返回NO_SNAPSHOT。
- AMZ同月替换只删除该平台、该年月在这两张报表表中的旧记录；不删除其他月、eBay记录或任何业务源表。发布失败整笔回滚。

`period_kind`原有VARCHAR(8)足以保存MONTHLY，本次没有扩列迁移。初始化SQL更新了中文注释；若此前已建表，CREATE IF NOT EXISTS不会改旧注释，不影响功能。

本功能的GET为只读业务查询，但首次查询或源变化时会物化更新这两张专用报表表；不修改源数据。数据库账号需要对新报表表有SELECT/INSERT/DELETE权限。

## 对外接口（供后续前端接入）

统一前缀：`/operations/{amz|ebay}/owner-sku/nature`。所有接口均GET。
返回沿用ERP的 `code/msg/data`；下表指data内容。

| 后缀 | 参数 | 内容 |
|---|---|---|
| `/summary` | `month`可选，默认当月 | 平台去重数、组别归属合计、各性质数量和占比、上月新品占比差 |
| `/groups` | `month` | 组别汇总items |
| `/owners` | `month`、`group_code`可选 | 各组负责人汇总，零SKU负责人可见 |
| `/details` | `month/group_code/owner_key/nature/sku/page/page_size` | 数据库分页明细；每页1–100条 |
| `/history` | start_month、end_month可选，YYYY-MM；include_current默认false | 默认最近12个日历月，可查更早区间；含首尾最多12个月，拒绝未来或倒序。缺月NO_SNAPSHOT；AMZ读MONTHLY，eBay读FROZEN。include_current=true且包含本月时，返回当月实时参考点并标记provisional，不提前冻结eBay |
| `/compare` | `base_month/target_month`必填；`scope=PLATFORM/GROUP/OWNER`、`group_code`可选 | 已保存月份指标增减；AMZ当月允许比较并标记provisional，eBay需已冻结 |

权限独立校验：

- AMZ：`operations:amzReplenishment:list`。
- eBay：`operations:ebayReplenishmentV2:list`。
- 无新增菜单权限SQL；不能只靠前端隐藏按钮。
- Java通过PerformancePythonClient转发至 `/api/v1/finance/{amz|ebay}-owner-sku/nature/...`；全部Python入口必须有内部Token。禁止浏览器绕过Java直连Python。

### 重要字段

`state`：READY/EMPTY/SOURCE_NOT_READY/MISSING_RULES/NO_SNAPSHOT。比较另可能为VERSION_MISMATCH。

- `sku_count` / `platform_deduplicated_count`：负责人＋完整销售SKU去重数。
- `group_attributed_count`：组别＋负责人＋完整销售SKU去重数。
- `cross_group_duplicate_count`：上述两数的差额。
- `detail_rows`：店铺/站点明细行数，不能当成去重SKU数。
- `counts`：NEW/OLD/UNKNOWN/CONFLICT，四类之和等于本级sku_count。
- `percentages`：**已经乘100**的两位小数字符串，如 `19.88` 表示19.88%；不得再乘100。空分母返回null。
- `new_share_change_pp`：新品占比环比的百分点差；无上月、版本不同、空分母返回null和comparison_reason。
- `owner_key`：规范化负责人姓名SHA256。当前规则表没有独立人员ID，因此姓名变更会形成新key；同时冻结owner_rule_key及匹配来源，不能跨姓名自动合并人员。
- `rule_version`：AMZ为 `amz-region-monthly-v3`，eBay为 `ebay-site-60d-v2`。不兼容版本不计算环比。
- `storage_policy`：AMZ为OVERWRITE_CURRENT_MONTH；eBay为MONTH_END_FREEZE。AMZ `live=true`表示当月可变，不代表额外保存一份LIVE数据。
- `batch_id`、`captured_at`、`source_batch`：计算批次、北京时间、源版本状态。

明细保留 `nature`（本店铺站点的判定）、`platform_nature`（平台去重判定）、`group_nature`（组内去重判定）、日期、刊登天数、阈值、local_sku、匹配来源及 `variants`。这里age_days是刊登距统计日的天数，不是海外仓库龄。
同一个最细粒度出现不同日期/local_sku时，variants保留原始判定，不任取一条。若全部一致则合并重复原始刊登。

明细nature筛选与当前下钻层级一致：未选组按platform_nature筛；选组按group_nature筛。这样点击“冲突”可以看到所有造成冲突的站点行，而不只是本行已冲突的数据。分页total是**明细行数**，排序为组别＋负责人键＋fact_key，稳定且不在前端全量分页。跨请求若源批次变化，前端应依据batch_id重新从第一页读取。

`sku`是完整销售SKU包含搜索，百分号/下划线按普通字符处理，不提供任意SQL排序字段。

- AMZ日期：**只读 `ods_lingxing_amz_listing_latest.open_date`**，不依赖 `amz_product_listing`，不回退到 `open_date_display`。ISO日期直接解析；实测欧洲站有日/月/年格式，按站点解析，例如英国 `07/06/2024 14:55:53 BST` 为2024-06-07；未知站点的斜杠日期不猜顺序。保留站点本地日历日期，不跨时区挪动日期。空日期为MISSING_LISTING_DATE，非空但无法解析为INVALID_OPEN_DATE，均归UNKNOWN；原文本保存在variants.open_date_raw。
- EU≤90天新品；US1/US2/US3分流组≤60天新品；未来日期保持原补货规则的有符号天数判定并标记FUTURE_LISTING_DATE；无法判组不猜阈值，显示UNKNOWN。
- eBay母集：`jmh_data_platform.ebay_product_listing.listing_status=1`；按完整MSKU匹配绩效品牌规则，不映射为JMH仓库SKU。
- eBay日期：全刊登表按site_name＋完整msku取MIN(listing_start_time)，本新报表改为≤60天新品；旧补货2.0保持不变。
- 任意组未匹配负责人为“未分配”，无法识别组为UNKNOWN_GROUP，均保留明细。
- 源和规则在同一REPEATABLE READ一致性快照中读取。实时缓存每次检查日期、源状态、规则和店铺映射指纹，不依赖仅按月份的过期缓存。
