# 店铺分析与采购优化：评估与实现说明

更新：2026-09-09。本说明替代此前未落地的实现草案。四项改动已接入代码；本轮没有启动服务、同步任务或删除业务数据。

## 一、评估后的决定

| 项目 | 实现 |
| --- | --- |
| 产品等级配置 | 9条数据库规则；按序号取首条命中；表头打开独立编辑器 |
| SKU分析库存 | 四列实时库存，分页后一次批量查询，与补货2.0共享库存SQL |
| 待采购删除 | 经用户明确授权新增；选中的待采购和已采购均可删，整批锁定、校验、删除 |
| 安全库存2/建议补货量2 | 复用原系数、时效与库存；以未取整预估销量2替换原月均销量 |

相比草案补正：

- 用 AST 的 Name 节点识别变量，不用字符串包含；等级与预估销量2的白名单隔离。
- 等级接口补齐 Java 转发、真实权限检查和保存审计。
- 保存前后端均校验完整9条规则，使用版本指纹和行锁拒绝覆盖他人的修改。
- 四项库存不参与订单明细的 SUM，避免一对多连接导致库存重复累计。
- 删除走 DELETE 请求体，避免大量ID拼接URL超长。没有新增角色授权。
- 第二组补货用未取整 Decimal 计算，不把页面两位小数重新作为输入。
- SQL的元数据锁、DDL自动提交不能忽略；回滚不再建议删表。

## 二、产品等级

配置表：`jmh_data_platform.ebay_replenishment_v2_level_rule`。

保留9条固定序号，页面可编辑条件、结果等级、说明和启用状态，不能新增/删除规则。初始化脚本只补缺行，绝不覆盖已有配置。

| 顺序 | 初始条件 | 等级 |
| --- | --- | --- |
| 1 | return_rate > 0.06 | C |
| 2 | return_rate >= 0.03 and profit_rate < 0.18 | C |
| 3 | return_rate >= 0.03 | B |
| 4 | profit_rate < 0.12 and sell_through_ratio <= 0.12 | C |
| 5 | profit_rate < 0.12 | B |
| 6 | profit_rate < 0.22 and sell_through_ratio < 0.12 | B |
| 7 | profit_rate < 0.22 | A |
| 8 | sell_through_ratio < 0.15 | B |
| 9 | true | S |

变量均为小数比率：退货率、利润率使用最近3个完整自然月汇总；动销比使用原预估销量/海外可售。6%写0.06。

表达式复用现有递归 AST 求值器，支持受限算术、比较和布尔运算，无 eval。每次列表查询只解析一次。若到达的规则引用了缺失变量，即使布尔短路可能绕过，也返回None；这是保持原分支链空值语义的必要条件。坏规则在原优先级阻断并记日志，不跳过。缺表、缺行、无规则命中时显示 --，不回退硬编码。

API：

- Python：`/api/v1/finance/ebay-replenishment-v2/level-rule` GET/POST，以及 POST `/level-rule/validate`。
- Java：`/operations/ebay/replenishment-v2/level-rule` GET/POST，以及 POST `/level-rule/validate`。
- 三个Java端点均要求 `operations:ebayReplenishmentV2:formula`；Python仍要求内部访问校验。
- GET返回 configs/revision；保存提交完整 configs/revision。操作人由Java登录用户写入，不信任浏览器传入的操作人。
- 编辑器输入停止500ms后校验；保存再次校验。规则已被他人修改时拒绝旧版本，重新打开编辑器后再编辑。

## 四、待采购删除

用户已明确授权新增该功能，但本轮没有实际执行采购删除。

- 前端复用选择框，支持单选、多选、跨页选择；两种状态均可选，导出只取其中待采购。删除前必须确认“永久删除、不可撤销”。
- 删除与导出互斥加载，避免同一页面连点冲突。
- `DELETE /procurement/pending-purchase`，JSON `{"ids":[1,2]}`，最多5000条，ID必须为正整数；不使用长URL参数。
- Java权限：`procurement:pendingPurchase:remove`，并记录DELETE操作日志。
- `@Transactional(rollbackFor = Exception.class)`：删除使用独立的 `SELECT ... FOR UPDATE` 查询锁住选中采购记录，允许status为0或1；导出仍只查status=0。
- 任一ID不存在或状态不属于0/1则整批拒绝；删除SQL再次限制status IN (0,1)，并检查受影响行数。数量不符抛错，事务回滚。
- 行锁让相同记录的导出和删除串行；先导出完成后可按新需求删除该已采购记录；先删除则后续导出失败。
- 数据库无需增加业务字段。06仅补按钮菜单，不自动授予角色。
- 删除无法从页面撤销；操作日志不是业务数据备份，恢复需依赖有效数据库备份。

## 五、第二组安全库存/建议补货量

```text
日销2 = 未取整预估销量2 / 30
安全库存2 = 日销2 × 总提前天数 × 安全系数
建议补货量2 = MAX(日销2 × 总提前天数 × 补货系数 - 四项库存合计, 0)
```

和原两个字段共用 `ebay_replenishment_v2_formula` 的S/A/B/C系数，不另建表或权限。全程Decimal；最后ROUND_HALF_UP取整数。时效、等级、系数、预估销量2任一依赖缺失返回None，不用0假装无需补货。

预测引擎默认仍返回两位小数，供已有试算使用；列表请求未取整值用于第二组计算，显示时仍按两位小数格式化。没有改变原安全库存和建议补货量的输入。点击任一安全库存/建议补货量表头均打开同一个系数弹窗，并明确提示影响两组字段、全部同级别SKU。

新两列放在原两列之后，建议补货量2固定右侧。保存时效后的局部重算回填四个字段，不替换整行、不覆盖正在编辑的输入。采购输入框原默认建议值来源保持不变。
