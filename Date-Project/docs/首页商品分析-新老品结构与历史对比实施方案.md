# 首页商品分析：AMZ／eBay 新老品结构与历史对比实施方案

> 原方案编制日期：2026-09-22。2026-09-23已按用户要求实现后端；前端第三排布局暂不实施，等待用户提供。部署及接口见《首页商品新老品报表-后端部署与接口.md》。用户明确选择保留旧eBay在售卡片，本轮只为新报表复用绩效归属并输出CL差异，不执行原方案中统一旧卡片的部分。数据库是否已执行以本轮交付记录为准。

## 1. 目标与边界

> AMZ最新确认优先：有有效刊登日期且美国≤60天／欧洲≤90天为新品，否则老品（包括缺失日期）。这替代原方案“AMZ缺日期未知”口径；eBay不改。

> 最新确认覆盖下文旧设计：图表移回第三排，两图各占一半。AMZ按补货区域配置分US/EU；eBay按站点＋完整MSKU最早刊登日期，≤60天新品、>60天老品，跨站点不合并；负责人规则不变。部署和JSON分区契约以配套交付文档“最新区域/站点口径”一节为准。

> 前端后续已获用户确认：不是第三排，改为首页第一排剩余两格放AMZ/eBay折线图；年月区间最多12个月，当前月暂计、历史缺月留空。实现与部署记录见配套交付文档。

> 2026-09-23 AMZ口径更新（优先于下文原设计）：只复用US≤60天、EU≤90天性质规则；日期只用ods_lingxing_amz_listing_latest.open_date，母集为status=1且is_delete=0，不复制补货的已配对、仓库或公式过滤，缺日期仍UNKNOWN。AMZ改为每年月一份MONTHLY数据，同月原子覆盖、跨月保留，不依赖旧amz_product_listing；eBay逻辑及月末冻结策略不变。具体部署、格式解析、历史版本处理以《首页商品新老品报表-后端部署与接口.md》为准。

在首页「商品分析」的现有「AMAZON · 在售商品」「EBAY · 在售商品」报表旁，分别增加 AMZ、eBay 的新老品结构报表。每个平台报表提供两个操作图标：「下钻明细」和「历史对比」。用户可在首页按**平台 → 业务组 → 绩效归属负责人 → 完整 SKU／店铺／站点**查看数量、占比和具体明细，并比较不同月份。

负责人归属的唯一依据是**计算绩效排名时使用的当月负责人规则和匹配函数**，不是人员姓名硬编码、补货快照上的 `principal_name`，也不是另一套首页规则。没有命中的 SKU 留在「未分配」，不从统计中消失。

本期只增加商品分析统计和历史快照；不改补货业务计算、利润计算、绩效排名结果，不从首页主动拉领星或 eBay 外部 API。现有在售 SKU 卡片可以在完成影响对账后，统一 eBay 的负责人匹配口径。

## 3. 人员归属统一：本需求的硬约束

### 3.1 当前月归属

1. 使用北京时间当前月 `YYYY-MM` 读取 `dwd_performance_owner_rule`，与绩效排名使用同一批规则。
2. AMZ 对每条在售刊登调用绩效归属路径 `_amazon_store_rules`、`_amazon_principal`。保留 US 店铺匹配、EU 品牌／OTH、UK 固定负责人、缺店铺归「未分配」等既有语义。`local_sku` 用于归属匹配，统计键仍为完整 `seller_sku`。
3. eBay 复用 `_ebay_assignment` 的匹配语义：FLL／LEJ、CL 固定负责人以及普通品牌规则。首页在售来源的 MSKU 是原始销售 SKU；是否引入绩效库存路径中的 `sku_map` 变换，必须通过样本对账确认，不能仅为了数字相同而隐式变换。
4. 归属结果必须同时保存 `principal_name`、`group_code`、`owner_match_source` 和规则月份；姓名只用于展示，查询与快照尽可能保存稳定规则键。规则冲突直接报错，不任意选一个人。
5. 未命中负责人保留「未分配」组内明细及数量；不要把所有规则中存在的人凭空生成 SKU 明细。零 SKU 负责人可以在汇总层展示，但不计入 SKU 总数。

### 3.2 eBay CL 差异处理

开发前输出一份只读差异报告：当前在售 CL MSKU 数、现首页归属、绩效规则归属、受影响的各负责人数量。新报表以绩效归属为准。经对账确认后，现有 eBay 首页卡片同步改为同一归属函数／规则，更新相关测试及口径说明。**不修改绩效排名本身，也不通过修改规则表消除差异。** 若差异报告出现比 CL 更广的异常，先排查映射和数据，再发布统一改动。

### 3.3 组别

组别应来自当月绩效规则的 `group_code` 与现有店铺／业务组判定，不按负责人姓名猜组。AMZ 需覆盖 EU、US1、US2 及现有 US3 业务分流（US2-MJ、US1-ZXY）；eBay 当前为 EBAY-1。店铺无法判组时进入「未识别组」，但不得丢掉 SKU。一个人可出现在多个组，不能仅靠姓名做全局组别映射。组别判定与人员归属可共用一次标准化后的规则上下文，避免各卡片各写一套。

## 4. 产品性质来源与口径

| 平台／组 | 补货页现行规则 | 新报表处理 |
|---|---|---|
| AMZ US 业务组 | `listing_create_date` 距统计日 ≤60 天为新品，否则老品 | 以同一日期字段和 60 天阈值判定；保留日期、阈值和来源 |
| AMZ EU | `listing_create_date` 距统计日 ≤90 天为新品，否则老品 | 同一日期字段、90 天阈值 |
| eBay | 同站点＋完整 MSKU 的 `MIN(listing_start_time)`；≤90 天新品 | 复用 `first_listing_date_by_sku` 的匹配条件及 `_product_nature` 语义 |

AMZ 补货 SQL 当前在 `listing_create_date IS NULL` 时落到「老品」。这不是可靠的产品年龄证据。新报表应新增「未知」并记录 `MISSING_LISTING_DATE`，**不要把日期缺失计为老品**；因此这类 SKU 与补货页显示可能不一致，必须在上线前出具差异数量，并在页面说明。不要为本报表悄悄修改补货页 SQL；是否同步修正补货页作为单独业务决策。

优先使用原始刊登日期计算，而不是直接读取补货快照的 `product_nature` 数值：补货快照可能未覆盖所有在售 SKU，且刷新时间与首页刊登源不一致。可用最新成功补货批次作**交叉核验**，但不能用其行数作为报表母集。实施前须用真实样本核验 AMZ `sid + seller_sku`、eBay `site_name + msku` 匹配率，以及不同店铺／站点同 SKU 日期不一致的情况。

性质编码统一为 `NEW`、`OLD`、`UNKNOWN`；跨组或跨站点同一平台去重 SKU 得出不同性质时标为 `CONFLICT`，在明细显示各原始判定，不暗中挑一条。当前月按北京时间当日判定；月末快照按实际采集日判定并冻结，历史不能再用今天的日期重算。

## 5. 统计粒度与可加总性

事实表最细粒度建议为 **平台＋组别＋负责人＋店铺 SID／ID＋站点＋完整销售 SKU**。关联价格、库存或补货时不得改变这个母集。PC 排除、缺 SKU 处理与现有首页一致，返回排除数和缺失数。

为避免“下钻求和却不等于首页”的误解，接口同时返回以下两类指标：

1. **平台去重 SKU（与现首页对账）**：AMZ `DISTINCT(负责人, seller_sku)`，eBay `DISTINCT(负责人, msku)`。同一负责人跨店铺只计一次。
2. **归属 SKU（用于组别下钻）**：`DISTINCT(平台, 组别, 负责人, SKU)`；同组跨店铺不重复，跨组分别计入各组。组别、个人、性质行可以逐层加总。

两者可能不同；平台卡片明确展示“平台去重总数”和“组别归属合计”，以及 `cross_group_duplicate_count`。店铺／站点原始明细行数是第三个数字，不能冒充 SKU 数。若同一去重键跨站点分类不同，平台性质结构使用 `CONFLICT`，确保 `NEW + OLD + UNKNOWN + CONFLICT = 平台去重 SKU`；组别内按本组的判定独立汇总。百分比的分母在每一级明确标注，不能将个人百分比相加。

**上线前对账条件：** 新服务的平台去重数必须等于统一口径后的现有首页在售卡片总数；不相等时先定位缺失、PC 排除、归属或重复键差异，不上线图表。

## 6. 前端交互

### 6.1 首页卡片

在 `RuoYi-Vue3-master/src/views/index.vue` 的商品分析区，现有 AMZ／eBay 在售卡片后各放一张新老品卡片。现有报表和价格分层不删除。布局在桌面两列、中屏两列、小屏单列，沿用现有响应式规则。

每张卡片显示：平台去重总数、新品／老品／未知／冲突数量及占比、上月新品占比变化（百分点）、源更新时间、规则月份／口径版本、异常提示。右上角两个独立图标按钮：

- **下钻明细**：打开抽屉，按平台 → 组别 → 负责人逐级展开；点击数量可在抽屉内分页查看 SKU／店铺／站点明细，支持性质筛选、SKU 搜索、按负责人和组别过滤。
- **历史对比**：打开弹窗，展示最近 12 个已冻结月份的数量和占比趋势；可选两个月比较平台、组别、负责人变化，并查看所选月份的冻结明细。未采集月份显示“无快照”，不显示 0。

当前月标「实时」，历史标「月末冻结」。本月尚无可比上月或跨口径版本时，变化值显示 `--` 和原因。图表颜色、图例与表格文字共同表达状态，不能只靠颜色；按钮具备 `aria-label` 和键盘操作。

### 6.2 明细字段

`platform`、`group_code`、`principal_name`、`store_id/sid`、`store_name`、`site`、`seller_sku/msku`、`local_sku`（有则显示）、`nature`、`first_listing_date`、`age_days`、`threshold_days`、`nature_source`、`owner_match_source`、`source_updated_at`、`snapshot_month`。冲突与未知提供原因。明细默认只展示必要业务字段，不暴露内部 Token 或数据库连接信息。

## 7. 后端与接口

沿用 **Vue → Spring Security 权限控制 → `PerformancePythonClient` → Python 内部鉴权 → MySQL**。不允许前端直接请求 Python 内网接口。现有权限可复用：AMZ `operations:amzReplenishment:list`，eBay `operations:ebayReplenishmentV2:list`；所有汇总、下钻、历史和导出入口分别校验权限，不能只隐藏按钮。

建议按平台复用现有 `/operations/{amz|ebay}/owner-sku` 入口，新增：

| Java 对外 GET | Python 内部对应功能 | 说明 |
|---|---|---|
| `/nature/summary` | 当前月实时或指定历史月汇总 | 返回两种总数、性质数量／占比、源状态、口径版本 |
| `/nature/groups` | 组别汇总 | 指定平台和月份 |
| `/nature/owners` | 指定组下负责人汇总 | `group_code` 白名单／参数化查询 |
| `/nature/details` | 分页 SKU 明细 | 月份、组别、负责人、性质、SKU 关键字；最大页大小 100 |
| `/nature/history` | 历史月份及趋势 | 最近 12 月；只读冻结快照 |
| `/nature/compare` | 两月同维度比较 | `base_month`、`target_month`，返回增减数量及百分点 |

接口返回 `state=READY/EMPTY/SOURCE_NOT_READY/MISSING_RULES/NO_SNAPSHOT`，不要把缺数据编码为 0。校验月份 `YYYY-MM`、平台枚举、性质枚举、页码／页大小；SQL 全部参数化。明细必须在数据库层分页，禁止先加载全量再由前端分页。当前月高频请求可按源批次＋规则月份做短时缓存，源变更或规则变更时失效；历史读快照无需重算。

## 8. 历史快照与调度

现有 `dws_home_inventory_sku_monthly` 仅有 AMZ／eBay 总数及摘要 JSON，不能提供历史新老品或人员明细。新增两张表，建议由 `Date-Project/migrations/` 提供幂等建表迁移：

1. `dws_home_product_nature_monthly`：月份、平台、组别、负责人、统计级别、去重／归属 SKU 数、NEW／OLD／UNKNOWN／CONFLICT 数、口径版本、源批次、规则月份、采集时间。设置唯一键 `(stat_month, platform, scope, group_code, owner_key, rule_version)`，用稳定占位值表示汇总层，不用可空列参与唯一约束。
2. `dwd_home_product_nature_sku_monthly`：月份及上述最细粒度、性质、首次刊登日期、负责人匹配来源、性质来源、异常原因、采集批次。唯一键需覆盖平台、组别、负责人、店铺、站点和完整 SKU；为月份＋平台＋组别＋负责人＋性质＋SKU 查询建索引。

新快照与现有首页在售 SKU 月度快照使用同一月末发布窗口。现有 Quartz 脚本 `RuoYi-Vue-springboot3/sql/20260921_home_inventory_sku_job.sql` 配置月末 23:50；实施时可扩展 `homeInventorySkuTask.captureMonthly()` 调用链，但必须保证：两平台源和当月规则均就绪、同月采集幂等、整月汇总／明细在一个成功批次发布、失败不留下半成品，已有历史月份不被后来规则覆盖。不要因补货批次缺失而清空已成功快照。

不能伪造上线前的历史。首次上线若仅有 2026-09 快照，历史图表就只显示 2026-09；现有首页总数快照不得被当作过去月份的新老品明细。历史快照冻结 `rule_version`，口径版本不同默认不做环比，升级须出具迁移与展示策略。

## 10. 实施顺序与验收

### 阶段 A：数据审计和口径对账（必须先完成）

1. AMZ US／EU、eBay 各抽样核对补货页性质与原始刊登日期，覆盖 60／90 天边界、日期缺失、同 SKU 跨店铺／站点。
2. 输出 eBay CL 归属差异报告；确认统一后的首页在售总数是否变化，哪些负责人增加／减少。
3. 统计 AMZ `sid + seller_sku`、eBay `site_name + msku` 的日期匹配率、未知率及跨组／跨站点冲突率。
4. 确认组别无法识别的数据量及可追溯原因。异常未解释前不进入 UI 发布。

### 阶段 B：实时统计与首页下钻

实现统一服务、分页接口、两张报表卡与下钻明细；同步修正 eBay 首页 CL 口径。验收：平台去重数与统一后的原首页数一致；各级 `NEW + OLD + UNKNOWN + CONFLICT = 本级 SKU 数`；组别归属合计与平台去重差异可解释。

### 阶段 C：月末快照与历史对比

先备份相关数据库并执行幂等迁移，再接入任务，模拟成功、重复执行、源未就绪、月切换和中途失败。验收：历史负责人和性质不会因今天的规则或日期变化而改变；无历史月显示无数据；跨版本不计算误导性环比。

### 阶段 D：性能、安全和发布回归

大批量在售 SKU 下检查 SQL 执行计划、索引与分页耗时；检查 Java 权限及 Python 内部 Token、参数化查询、越权访问、异常日志脱敏。运行现有首页、补货、绩效排名相关回归测试及前端生产构建；先在开发环境核对，再部署生产。新接口不调用外部 API、不写补货或绩效业务表。

## 12. 预估工作量与待确认项

在源表键值和日期匹配率达标的前提下，预计数据审计／口径对账 1～2 天，实时接口与前端 2～3 天，历史快照与调度 1～2 天，回归及部署 1～2 天。若发现 AMZ 店铺组别或跨站点性质大量冲突，需要单独调整排期。

实施前仅有两项需要业务方确认：

1. eBay CL 按绩效固定归属统一旧首页卡片后，各负责人的历史可比性从新口径上线月开始，是否接受？本文建议接受并标记口径版本，不回写旧月。
2. AMZ 补货页把缺日期显示为老品，新首页报表显示未知。本文建议先保持补货页不变、在报表中明确差异，后续再单独评估是否修正补货页。

这两项不影响先做只读数据审计；未确认前不得发布会改变旧首页归属或业务认知的展示。
