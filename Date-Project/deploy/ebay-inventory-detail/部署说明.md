# Ebay库存明细完整部署包（2026-09-17）

本包适用于已有 JMH ERP（Java、Vue、Python）环境，不是空库安装包。默认 Python 库为 `date-project`，Java/来源库为 `jmh_data_platform`；若部署配置不同，先统一修改脚本中的库名。

## 先确认代码版本

本包对应本地提交 `2467c41` 及其之前的库存明细功能，包含历史导入、单价导入、中间码合并和导入导出下拉菜单。本包制作时该提交尚未成功推送 GitHub，不能认为部署机仅 git pull 就能取得它。请先确认取得对应代码（或包含该提交的后续版本），再编译、部署。

SQL 不包含本地业务数据、Excel 文件、密码或 API 密钥，也不会自动拉取数据、导入文件、生成快照。

## 执行顺序

部署前备份两个数据库，暂停会写库存历史的周报任务，避免用户刷新/导入。MySQL 8 环境按下列顺序逐个完整执行文件；任意报错立即停止，不要使用 `--force`，不要把整个上级“部署sql”目录批量执行。

1. 执行 `00_部署前检查_只读.sql`。专用表不存在属于首次部署正常现象；基础系统表、两个数据库必须已存在。检查目录、有效用户及角色。
2. 如果共享源表缺失，先按后面的“共享依赖”说明处理。已有源表不要清空、重建或导入本地数据。
3. 依次执行 `01_产品等级表.sql` → `02_历史透视表.sql` → `03_明细历史表.sql` → `04_产品单价表.sql` → `05_历史导入行标识.sql` → `06_页面菜单与leiyongyu权限.sql`。
4. 部署匹配版本的 Python、重新编译的 Java JAR 和 Vue 生产 dist，重启 Python/Java，更新前端静态资源。SQL 不能代替代码发布。
5. 退出 leiyongyu 账号并重新登录，执行 `99_部署后验证_只读.sql`。权限三项必须都存在、启用且已授权；历史行唯一索引必须为新四列索引。
6. 查看“运营中心 → eBay → Ebay库存明细”。导入等级、单价后点击“刷新”，使用现有源数据重新计算今天的明细和透视。同日覆盖，跨日保留；不需要重新拉接口才可计算。

可用数据库客户端执行整份文件；或在已连接的 mysql 客户端输入 `SOURCE D:/部署目录/01_产品等级表.sql;`。各文件含 USE 库名，不要依赖客户端当前选中的库。

### 本页面专用的全部 5 张表

全部位于 `date-project`：

| 表 | 用途 | 脚本 |
| --- | --- | --- |
| ebay_inventory_detail_grade | 站点+完整SKU产品等级；上传增量覆盖 | 01 |
| ebay_inventory_pivot_snapshot | 每统计日期唯一的共享批次主表 | 02 |
| ebay_inventory_pivot_owner | 批次下负责人+站点历史汇总 | 02 |
| ebay_inventory_detail_history | 历史明细 JSON；与透视共用日期批次 | 03、05 |
| ebay_inventory_detail_price | 上传的SKU+单价；中间码取最低人民币价 | 04 |

01—04 仅 CREATE TABLE IF NOT EXISTS，不覆盖已存在表和数据。05 给历史表增加 `record_key` 并将唯一键从 `(snapshot_id,site,sku)` 改为 `(snapshot_id,site,sku,record_key)`，保留原数据，让导入的重复/空SKU原始行也能保存。它是 ALTER TABLE，会发生 DDL 提交及可能的锁表，不能靠 ROLLBACK 撤销，建议低峰执行。已部署过的环境也不能漏 05；重复执行不会重新导入数据。CREATE IF NOT EXISTS 不会自动修复任意旧结构，异常时停止核查，禁止删表重建。

## 权限 SQL

执行 **06_页面菜单与leiyongyu权限.sql** 即可建菜单并授权，不需要再执行上级目录的全系统授权脚本。

| 权限 | 当前实际用途 |
| --- | --- |
| operations:ebayInventoryDetail:list | 查看明细、历史日期、负责人透视 |
| operations:ebayInventoryDetail:import | 等级导入、单价导入、历史导入、刷新重算 |
| operations:ebayInventoryDetail:export | 明细及透视导出 |

脚本按目录路径和 perms 查 ID，不写死 menu_id/role_id，补齐“运营中心/eBay”祖先权限。授予 **leiyongyu 当前全部有效角色** 本页面三项权限，并非授予所有系统权限。不新建账号/角色、不改变角色绑定、不执行数据库 GRANT。注意共享这些角色的其他用户也会获得页面权限。

既有菜单人工禁用/隐藏状态不会强制恢复。若角色/账号已停用、leiyongyu 不存在或父目录缺失，先处理检查结果，不要硬改菜单编号。旧导入权限菜单名可能仍叫“导入产品等级”，但 perms 同一条，实际涵盖三种导入和刷新。

## 定时任务与数据更新

**2026-09-17补充：缺少两个谷仓任务时，直接执行本目录07、08，再执行09验证。** 详细入口和顺序见《谷仓两项定时任务部署说明.md》。07/08已去掉旧月度库龄数据复制，不必再执行参考目录中重复的任务脚本。执行后重启Java加载Quartz；新任务默认启用，已有任务保留人工启停状态。

本页不再另建一套重复调度。沿用已有链路，先检查 00 输出的 sys_job：

| 任务调用目标 | 计划 | 作用 |
| --- | --- | --- |
| operationSyncTask.syncGoodcangInventoryAgeLatest() | 周一06:00 | 最新库龄；不替换原月度库龄任务 |
| pythonGoodcangStorageTask.runWeekly() | 周一07:00 | 近30天仓租概要后逐单明细 |

Java 时区按 Asia/Shanghai 核对。三个任务不是跨任务强制依赖：前一个执行失败或超时，不保证后一个取得更新后的数据；需要看各自成功时间。手动点击页面刷新只计算，不拉取以上接口。

`参考_原有上游任务脚本` 提供已有任务的原始脚本，**不在本页01—06必执行列表内**。任务已存在就不重复创建。缺失任务才按其脚本注释评估执行：仓租脚本涉及 Python scheduler_task；库龄脚本会在 latest 为空时尝试复制月表数据（要求原月表存在），并添加/更新周任务；周报脚本还涉及脚本菜单。因此不要整目录自动执行。修改 sys_job 后按现有方式重启 Java/重新加载调度，使运行时生效。库龄只想补建空 latest 表时，用可选共享源表文件，不用执行带历史复制的任务脚本。

## 导入及验收

- 首次没有每日明细时，核实源数据成功批次后点击刷新生成今天记录。`ops_weekly_export_file` 的成功/删除状态登记必须与库存批次一致，孤立ODS行不会被当成成功来源。
- 产品等级按站点+完整SKU增量更新；单价按本次涉及SKU替换其价格集合，其他SKU不动，中间码取最低价。上传后刷新重算今天，旧日期不会套用新单价重算。
- 历史Excel从“导出”旁下拉选择历史导入，仅识别 US/DE/UK 三个指定 sheet。只填历史原始明细，不重算公式、不生成历史透视；重复原始行保留；空、0、错误等显示 --。同文件重传幂等，不同文件与已有日期冲突会整份拒绝。
- 历史上传最大50MiB（解压上限300MiB、10万行），其他导入10MiB；核对反向代理请求体上限和上传超时，历史请求允许300秒。不要只改前端超时而忽略 Nginx 等代理。
- 刷新后同日期只有一个主批次；明细可翻页，日期可切换，透视负责人汇总显示红色；选中导出与全部筛选导出均测试。
- 99 校验查看数据条数、批次关联及权限。空表不一定是部署失败，但必须按对应上游流程导入/同步真实数据后才能验业务数值。
